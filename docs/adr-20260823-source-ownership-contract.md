# ADR: Source Ownership Contract

Date: 2026-08-23

Status: Accepted for IDENTITY-02 implementation

Package: `@egose/n8n-sync`

## Context

Subscriber ordering is scoped by `(sourceId, entityKind, sourceEntityId)`, but workflow and credential mutation currently uses the source-provided entity id as the target primary key. That lets a publisher overwrite, archive, or delete a native target row when its source-local id matches a target id. It also lets two publishers that use the same workflow or credential id race on one target row even though their ordering checkpoints are independent.

The current authentication model uses one shared credential for all publishers. Any holder of that credential can put any `sourceId` in the signed body, so the `sourceId` namespace is not an isolation boundary.

DESIGN-01 selected package-owned metadata tables in the same n8n Postgres database. This ADR defines the identity and ownership policy those tables must enforce.

## Decision

Support multi-source aggregation. A subscriber may accept events from multiple source instances, but every source must have an explicit durable source record and source-bound authentication credential. Source-local workflow and credential IDs are identifiers only inside that source namespace; they are never used as target primary keys for new rows.

For workflows and credentials, the subscriber must maintain a durable mapping:

- `(source_id, entity_kind, source_entity_id) -> target_entity_id`
- `entity_kind` is `workflow` or `credential`
- `target_entity_id` is generated by the target subscriber
- `(entity_kind, target_entity_id)` is unique and owned by at most one source entity

Native target rows are rows without an ownership mapping. Sync may not update, archive, or delete a native row unless an explicit migration has first claimed that row with unambiguous operator-supplied ownership metadata.

Execution identity keeps the existing source-scoped mapping shape selected by DESIGN-01 and must refer to the mapped target workflow id, not to a source-local workflow id.

## Schema

IDENTITY-02 should extend the DESIGN-01 metadata schema to this concrete ownership shape:

```sql
create table if not exists n8n_sync_source (
  source_id text primary key,
  source_epoch text not null,
  status text not null default 'active' check (status in ('active', 'retired')),
  retired_at timestamptz,
  successor_source_id text references n8n_sync_source(source_id),
  first_seen_at timestamptz not null default now(),
  last_seen_at timestamptz not null default now()
);

create table if not exists n8n_sync_source_auth (
  auth_key_id text primary key,
  source_id text not null references n8n_sync_source(source_id),
  auth_mode text not null check (auth_mode in ('hmac', 'token')),
  credential_fingerprint text not null,
  created_at timestamptz not null default now(),
  revoked_at timestamptz,
  unique (source_id, auth_key_id)
);

create table if not exists n8n_sync_entity_state (
  source_id text not null references n8n_sync_source(source_id),
  entity_kind text not null check (entity_kind in ('workflow', 'credential', 'execution')),
  source_entity_id text not null,
  target_entity_id text,
  last_event_id text not null,
  last_revision numeric(78, 0) not null,
  last_event_type text not null,
  entity_updated_at timestamptz,
  deleted_at timestamptz,
  archived_at timestamptz,
  ownership_status text not null default 'owned' check (ownership_status in ('owned', 'deleted', 'transferred')),
  transferred_to_source_id text,
  updated_at timestamptz not null default now(),
  primary key (source_id, entity_kind, source_entity_id),
  unique (entity_kind, target_entity_id)
);

create table if not exists n8n_sync_execution_identity (
  source_id text not null references n8n_sync_source(source_id),
  source_execution_id text not null,
  target_execution_id text not null,
  source_workflow_id text not null,
  target_workflow_id text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (source_id, source_execution_id),
  unique (target_execution_id)
);
```

`n8n_sync_entity_state` is both the ordering row and ownership mapping for workflows and credentials. When `entity_kind = 'execution'`, `target_entity_id` may be null if execution ordering and execution identity remain split during implementation; EXECUTION-01 owns the final execution mapping mechanics.

Secrets must not be stored in these tables. `credential_fingerprint` is a non-secret stable fingerprint used for diagnostics and mismatch detection. Actual HMAC secrets or bearer tokens are supplied through subscriber configuration or a future secret provider.

## Authentication Binding

Authentication credentials must bind to one source id. A global shared secret is not a valid isolation boundary for multi-source mode.

The subscriber configuration must define source-bound credentials, for example as a JSON value equivalent to:

```json
[
  {
    "sourceId": "prod-us",
    "sourceEpoch": "2026-08-prod-us",
    "authKeyId": "prod-us-1", // pragma: allowlist secret
    "mode": "hmac",
    "secret": "..."
  },
  {
    "sourceId": "prod-eu",
    "sourceEpoch": "2026-08-prod-eu",
    "authKeyId": "prod-eu-1", // pragma: allowlist secret
    "mode": "hmac",
    "secret": "..."
  }
]
```

HMAC requests must carry a non-secret key selector header, tentatively `x-sync-key-id`, so the subscriber can select the correct secret before parsing the signed body. Token mode must map the presented token to exactly one source record. After authentication and JSON validation, the subscriber must compare `event.sourceId` with the authenticated source id.

Request outcomes:

- Missing key id, unknown key id, revoked key, bad signature, or bad bearer token returns `401 { "error": "unauthorized" }`.
- A valid credential whose bound source does not equal `event.sourceId` returns non-retryable `403 { "error": "sync source forbidden", "code": "SYNC_SOURCE_FORBIDDEN" }`.
- A valid credential for a retired source returns non-retryable `410 { "error": "sync source retired", "code": "SYNC_SOURCE_RETIRED" }`.
- A valid event for an unregistered active source returns non-retryable `403 { "error": "sync source forbidden", "code": "SYNC_SOURCE_FORBIDDEN" }`; sources must be provisioned before traffic.

## Request Outcomes And Ownership Rules

For workflow and credential upserts:

- If mapping exists for `(source_id, entity_kind, source_entity_id)`, update that `target_entity_id` only.
- If no mapping exists, generate a new target id and insert the target row plus mapping in one transaction.
- If target-id generation collides with any existing native or synced row, retry generation inside the transaction or return retryable `500`; never update the colliding row.
- If metadata claims a `target_entity_id` but the target row is missing, return retryable `500 { "error": "failed to apply sync event" }` until repair tooling or resync can reconcile the mismatch. Do not silently create a second mapping.

For workflow archives and deletes:

- If mapping exists, mutate only the mapped target row and retain the ordering tombstone.
- If no mapping exists, record the stale-protection tombstone for that source entity and do not touch any target row with the same id.
- A delete must never remove a native target row.

For credential deletes:

- If mapping exists, delete only the mapped target credential and retain the ordering tombstone.
- If no mapping exists, record the source-scoped tombstone and do not touch a native target credential with the same id.

For cross-source conflicts:

- Two sources may use the same source-local workflow or credential id. They receive distinct target ids and independent ordering state.
- A source may not claim another source's existing `target_entity_id`. If metadata uniqueness detects this, return non-retryable `409 { "error": "sync ownership conflict", "code": "SYNC_OWNERSHIP_CONFLICT" }` and leave rows unchanged.

Existing `SYNC_REVISION_CONFLICT`, `SYNC_ENTITY_TIMESTAMP_CONFLICT`, and `SYNC_ENTITY_DISABLED` responses continue to apply after source/auth/ownership gates pass.

## Deletion And Tombstone Retention

Workflow and credential deletes mark `ownership_status = 'deleted'`, set `deleted_at`, keep `target_entity_id`, and keep `last_revision` and `last_event_id`. The target row may be physically deleted, but the mapping row remains as the source-scoped tombstone.

Delete tombstones must not expire until SOURCE-01 provides a source epoch/checkpoint protocol that proves older events from that source cannot be delivered. Retiring a source does not automatically delete tombstones.

## Source Retirement

Source retirement is an explicit operator action that sets `n8n_sync_source.status = 'retired'` and `retired_at`. After retirement:

- New events for the source return `410 SYNC_SOURCE_RETIRED`.
- Existing mapped target rows remain unless the operator separately requests cleanup.
- Tombstones and mappings remain for audit and stale-event protection.
- Cleanup may delete mapped target rows and metadata only when the operator accepts that future events from the retired source will be rejected by source status before ordering checks.

## Ownership Transfer

Ownership transfer is an explicit offline migration, not an event type. The operator must quiesce the old and new sources, provide a manifest mapping old source entity ids to new source entity ids, and update metadata in one transaction:

- Insert or validate the successor `n8n_sync_source` row.
- Move or copy `target_entity_id` ownership from `(old_source_id, kind, old_source_entity_id)` to `(new_source_id, kind, new_source_entity_id)`.
- Mark the old row `ownership_status = 'transferred'` and set `transferred_to_source_id`.
- Preserve the old row's last revision as a tombstone against stale old-source events.
- Require the new source to start from a higher source epoch or fresh revision namespace recorded by SOURCE-01.

If the manifest is incomplete or would map two live source entities to one target row, the transfer must abort with no partial changes.

## Migration Of Existing Target IDs

Existing installations may have synced rows whose target primary key equals the source-local id and no ownership metadata. Automatic migration is unsafe because the subscriber cannot distinguish native rows from previously synced rows.

IDENTITY-02 migration must therefore be explicit:

1. Stop subscriber traffic and back up the n8n database plus existing JSON state files.
2. Run a dry-run inventory that lists workflow and credential rows whose ids overlap with source-local ids found in format-2 ordering state or operator-supplied source exports.
3. Require an operator manifest with `sourceId`, `entityKind`, `sourceEntityId`, `targetEntityId`, and `ownership` for each row to claim.
4. Import only rows marked as `synced-owned`; create metadata mappings and preserve current target ids for those rows.
5. Leave rows marked `native` unclaimed. Future source events with the same source-local id must create a new generated target id rather than mutating the native row.
6. If a row is ambiguous or omitted, fail startup with migration guidance; do not guess ownership from id equality, name, timestamps, or project membership.
7. After migration, run a full source resync so mapped target rows are updated by source namespace rather than by primary-key equality.

New installations must not preserve source-local ids as target ids. They must generate target ids from the start.

## Rejected Alternatives

Single authoritative source per subscriber is rejected. It would be simpler, but it discards the existing `sourceId`-scoped ordering model and still needs durable native-row collision protection. Operators also commonly use one target for fan-in staging or promotion, so single-source mode would force unnecessary target instances.

Using source-provided workflow and credential ids as target primary keys with a `(sourceId, id)` ordering key is rejected because it is the root collision defect. Ordering isolation does not isolate target-row mutation.

Prefixing target ids with `sourceId` is rejected because n8n ids are externally visible and may have length/format assumptions. It also does not protect native rows when prefixes collide or when legacy rows already exist.

Name-based matching is rejected because names are mutable, non-unique, and not a security boundary.

Trusting a global shared secret plus body `sourceId` is rejected because every authorized publisher can impersonate every other source.

Auto-claiming existing target rows during migration is rejected because id equality is not proof of prior sync ownership.

## Proof-Of-Concept Tests

The selected behavior is modeled by `packages/n8n-sync/tests/identity-contract.spec.ts`.

Run the targeted proof command with:

```bash
pnpm --filter @egose/n8n-sync test -- tests/identity-contract.spec.ts
```

The POC demonstrates:

- A source-local workflow id that collides with a native target workflow creates a distinct mapped target row, and delete only removes the mapped row.
- A source-local credential id that collides with a native target credential creates a distinct mapped target row, and delete only removes the mapped row.
- Two sources using the same source-local workflow id receive separate target workflow ids.
- Two sources using the same source-local credential id receive separate target credential ids.
- A credential bound to one source cannot authenticate a request that claims another source id.

These are contract tests, not production enforcement. IDENTITY-02 must replace the in-memory POC with transactional metadata enforcement at the applier/auth boundaries without changing these outcomes.

## Residual Risks

Production code still mutates workflows and credentials by source-provided primary key until IDENTITY-02 is implemented. This ADR only selects the policy and provides executable POC behavior.

The exact header/config names for source-bound credentials may change during AUTH-01/SOURCE-01 implementation, but the invariant may not: each accepted request must authenticate as exactly one source and the event body must claim that same source.

Target-generated id format should use n8n's runtime id generation where available. If IDENTITY-02 must generate ids directly, it needs pinned-runtime integration tests proving the generated ids satisfy n8n constraints for workflows, credentials, shared ownership rows, and Public API reads.
