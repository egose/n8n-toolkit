# @egose/n8n-sync

Sync n8n credentials and workflows between n8n instances using [n8n external hooks](https://docs.n8n.io/deploy/host-n8n/configure-n8n/external-hooks/).

The package builds two self-contained CommonJS hook bundles:

| Bundle                | Role                                                                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `dist/publisher.cjs`  | Runs on the **source** instance. Lifecycle hooks POST sync events to one or more subscribers over HTTPS.                     |
| `dist/subscriber.cjs` | Runs on each **target** instance. Mounts an endpoint on n8n's own server and applies events via n8n's internal repositories. |

## Supported n8n versions

The subscriber runtime adapter is pinned and contract-tested against this matrix:

| Channel | Version  |
| ------- | -------- |
| current | `2.31.2` |

The repo-root `pnpm test:integration` command runs the Docker-backed sync suite across that matrix. Set `N8N_VERSION=<tag>` to debug a single pinned version locally.

## How it works

```
┌──────────────┐   credentials.create/update/delete      ┌──────────────┐
│  source n8n  │   workflow.afterCreate/afterUpdate/…    │  target n8n  │
│              │ ──────────────────────────────────────► │   (1..n)     │
│ publisher.cjs│   POST /rest/sync/v1/events             │subscriber.cjs│
│              │   HMAC-signed or bearer-token auth      │              │
└──────────────┘                                         └──────────────┘
```

- **Fan-out**: the publisher delivers every event to every URL in `SYNC_SUBSCRIBER_URLS`. Hook preparation and emission are serialized per source entity before fan-out, and each target has its own **serialized delivery queue**. Events for one entity reach a given target in hook invocation order, while unrelated entities and slow or unreachable targets do not delay each other. Only exact queued duplicates of the same semantic operation are coalesced; mixed operations stay in order.
- **Fire-and-forget hooks**: deliveries run in the background and failures are retried (1s, 2s, 4s, capped at 10s) then logged, so a sync outage cannot break n8n operations. The publisher never throws.
- Every emitted event carries a source-scoped `eventId` plus a monotonic per-entity `entityRevision`. When delivery is enabled, `SYNC_SOURCE_ID` must be explicit, non-blank, and within the subscriber's 512-character wire limit; the publisher persists that source ID and its counters under `SYNC_PUBLISHER_STATE_PATH`, so container hostnames or replacement pods cannot silently change the logical source. If preparation is dropped because the hook did not expose a stable identity, a repository lookup failed, tag state is unresolved, or a required lifecycle timestamp is missing, no event is emitted and no revision is consumed; later same-entity hooks continue after the drop.
- The subscriber applies events **idempotently within the current source-scoped ordering model**, using the target instance's own TypeORM repositories (resolved from n8n's DI container at runtime), conditional timestamp updates for workflow/credential/execution last-write-wins guards, and file-backed ordering state plus delete tombstones under `SYNC_SUBSCRIBER_STATE_PATH`. Current workflow and credential production writes still use source-provided IDs as target primary keys; the accepted multi-source ownership policy is documented in `docs/adr-20260823-source-ownership-contract.md` but is not yet enforced by production metadata.
- Credential sync accepts only the stored **encrypted string blob** on the wire. Plain object payloads are dropped or rejected to avoid relying on undocumented repository-side encryption semantics. All instances must still share the same `N8N_ENCRYPTION_KEY` so targets can decrypt secrets at runtime.

## Tag-based filtering

The publisher can restrict and rewrite sync events based on n8n workflow tags. Enable it on a source instance with `SYNC_FILTER_BY_TAG=true`; the subscriber side is unaffected.

| Tag (default name)           | Effect                                                                                                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sync` (`SYNC_WORKFLOW_TAG`) | Workflow is eligible for syncing. Without it the publisher emits `workflow.delete` for that id (targets remove it).                                                                |
| `active` (`SYNC_ACTIVE_TAG`) | With the `sync` tag present, presence of this tag rewrites the DTO `active` to `true`; absence rewrites it to `false`. The source's real value is preserved in `meta.active_real`. |

Rules when `SYNC_FILTER_BY_TAG=true`:

- **Sync tag missing** → `workflow.afterCreate`, `workflow.afterUpdate`, and `workflow.activate` emit `workflow.delete` instead of upsert (so targets converge to "absent").
- **Sync tag present, `active` tag missing** → DTO `active=false`, `meta.active_real` holds the real source value.
- **Sync tag present, `active` tag present** → DTO `active=true`, `meta.active_real` holds the real source value.
- **Execution events** (`workflow.postExecute`) for workflows lacking the sync tag are silently dropped (no `workflow.delete` is emitted for executions).
- **Tag resolution** — n8n's hook payload sometimes passes an inline `tags` array; otherwise the publisher falls back to `dbCollections.Workflow.findOne({ relations: ['tags'] })`.

When `SYNC_FILTER_BY_TAG=false` (default): all workflows pass through unmodified, the DTO carries no `tags` field, and no `meta.active_real` is set. No tag-resolving DB queries run.

## Authentication

Two schemes are available via `SYNC_AUTH_MODE` (must match on both sides):

| Mode             | Headers                                | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hmac` (default) | `x-sync-timestamp`, `x-sync-signature` | Per-request HMAC-SHA256 of `<timestamp>.<rawBody>` keyed with the shared secret. Replay-protected: the subscriber rejects timestamps outside a 5-minute tolerance and rejects an exact re-send of the same signed request from a bounded in-memory replay cache after success, and while the first matching request is still in flight. Failed parse, validation, or application attempts release their reservation so the exact request can be retried. Every publisher retry re-signs with a fresh timestamp. |
| `token`          | `x-sync-token`                         | Static shared-secret bearer token. Simpler; use only over TLS. Delivery remains idempotent via `eventId` / `entityRevision`, but token mode does not reject request replay at the auth boundary.                                                                                                                                                                                                                                                                                                                |

Requests must use `Content-Type: application/json`; unsupported `Content-Encoding` values are rejected.

In `hmac` mode the subscriber authenticates the exact raw request bytes before JSON parsing, then parses and applies those same bytes. It uses `req.rawBody` when n8n's global `rawBodyReader` is present, otherwise it reads the unread request stream itself, and it fails closed if only a pre-parsed `req.body` is available. If both `req.rawBody` and `req.body` exist, `req.body` is ignored so a divergent pre-parsed object cannot be applied under a signature for different bytes.

In `token` mode the subscriber still enforces the same JSON content-type and size limits, but it may reuse an already parsed `req.body` because authentication does not depend on the raw bytes.

Every valid sync event also includes:

- `eventId` — unique within a publisher source (`<sourceId>:<sequence>`)
- `entityRevision` — decimal-string revision monotonic for that `(sourceId, entity)`

The subscriber uses `entityRevision` as the tie-breaker when two distinct mutations share the same source timestamp. Subscriber ordering state is versioned as format `2` and keys each checkpoint with a JSON tuple `[sourceId, entityKind, entityId]`, so colons or other punctuation inside source and entity IDs cannot merge two sources or entities. After revision ordering accepts a newer event, an equal workflow/credential `updatedAt` or execution `stoppedAt` is allowed to update the target row. A newer revision with an older entity timestamp is treated as an application conflict and is not recorded in subscriber ordering state, so a corrected redelivery can still apply.

Subscriber ordering format `1` used ambiguous colon-separated keys and is not safely reversible. A subscriber that finds a version-1 `SYNC_SUBSCRIBER_STATE_PATH` refuses startup/event handling with guidance to back up the file, restore from unambiguous metadata if available, or reset subscriber sync state and run a full source resync so tombstones and revisions are rebuilt. Do not delete or rewrite this file without first planning for stale delete protection.

If a distinct `eventId` reuses an already applied `entityRevision` for the same `(sourceId, entity)`, the subscriber returns HTTP `409` with `{ "error": "sync revision conflict", "code": "SYNC_REVISION_CONFLICT" }`. The event is not applied, and the subscriber does not modify the entity row or durable ordering checkpoint. This is a protocol conflict, not a retryable server failure; the publisher's HTTP client treats `409` as non-retryable. Exact duplicate deliveries with the same `eventId` and `entityRevision` remain idempotent and receive `200 { "ok": true }`.

If the subscriber receives a valid event for an entity family disabled by `SYNC_ENTITIES`, it returns HTTP `422` with `{ "error": "sync entity disabled", "code": "SYNC_ENTITY_DISABLED", "entity": "workflows" | "credentials" | "executions" }`. Authentication and wire validation still run first, but the disabled event is rejected before repository access or subscriber ordering/identity state mutation. The publisher treats this 4xx response as non-retryable. At startup the subscriber also skips resolving disabled workflow, credential, and execution repository services where the selected entity set does not require them.

## Wired hooks

| Source hook                                         | Event                | Entity       |
| --------------------------------------------------- | -------------------- | ------------ |
| `credentials.create` / `credentials.update`         | `credentials.upsert` | credentials  |
| `credentials.delete`                                | `credentials.delete` | credentials  |
| `workflow.afterCreate` / `workflow.afterUpdate`     | `workflow.upsert`    | workflows    |
| `workflow.activate`                                 | `workflow.activate`  | workflows    |
| `workflow.afterDelete`                              | `workflow.delete`    | workflows    |
| `workflow.afterArchive` / `workflow.afterUnarchive` | `workflow.archive`   | workflows    |
| `workflow.postExecute`                              | `execution.upsert`   | executions ★ |

★ `workflow.postExecute` is **opt-in** — see `SYNC_ENTITIES`. It fires per execution (high volume) and the publisher handler is fire-and-forget so it never blocks n8n. The DTO carries only the scalar lifecycle columns exposed by that hook (`id`, `workflowId`, `status`, `mode`, `finished`, `startedAt`, `stoppedAt`); per-step `fullRunData` is dropped to keep payloads small.

Credential hook contract, pinned to the n8n `2.31.2` image used by this repository's example builds:

- `credentials.create` and `credentials.update` publish only when the hook payload or resolved repository row includes the stable row `id` plus an encrypted string `data` blob.
- When `credentials.create` includes an `id` but the row is not yet queryable, the publisher retries `dbCollections.Credentials.findOne({ where: { id } })` briefly in the background and emits only that exact row when the stored `data` is the encrypted string blob.
- Payloads without a stable credential `id` are unsupported for sync publication and are dropped with a warning instead of guessing by `{name, type}`.
- Object-form credential payloads are unsupported for sync publication and are dropped with a warning; the subscriber also rejects them if they bypass publisher validation.

## Setup

Build the bundles (`pnpm --filter @egose/n8n-sync build`), copy them to both instances, and point n8n at the appropriate file via `EXTERNAL_HOOK_FILES`.

### Source instance (publisher)

```bash
export EXTERNAL_HOOK_FILES=/path/to/publisher.cjs
export SYNC_SUBSCRIBER_URLS=https://n8n-target-a.example.com,https://n8n-target-b.example.com
export SYNC_SOURCE_ID=prod-source-a
export SYNC_SHARED_SECRET=<shared-secret>
```

### Target instance(s) (subscriber)

```bash
export EXTERNAL_HOOK_FILES=/path/to/subscriber.cjs
export SYNC_SHARED_SECRET=<shared-secret>
# optional:
export SYNC_TARGET_PROJECT_ID=<project-id>   # link synced entities to this project
```

Restart both instances. The subscriber mounts unauthenticated liveness and readiness probes at `GET /rest/sync/v1/health` and `GET /rest/sync/v1/ready`. `/health` returns 200 once the route is mounted; `/ready` returns 200 only while required file-backed state is loaded and writable. `POST /rest/sync/v1/events` returns `503 { "ok": false, "ready": false }` while readiness is false.

## Persistence, Readiness, And Recovery

- Persist `SYNC_PUBLISHER_STATE_PATH`, its adjacent `.lock` file, `SYNC_SUBSCRIBER_STATE_PATH`, and the derived subscriber execution identity file when execution sync is enabled. These files are part of sync state, not cache.
- The publisher queue is in memory. Events not yet delivered at process exit and events dropped because `SYNC_MAX_QUEUE_SIZE` is full are lost. Later upserts may converge state, but dropped deletes, archives, and execution updates are not reconstructed automatically.
- Publisher and subscriber JSON state writes are atomic file replacements for a single file only. They are not atomic with each other or with n8n database mutations. A crash between a database mutation and JSON checkpoint can still require operator repair or full source resync until the blocked transactional metadata work is implemented and verified.
- Supported production topology is one publisher process for a given `SYNC_SOURCE_ID`/`SYNC_PUBLISHER_STATE_PATH` and one subscriber process for a given route/state path. The publisher lock is best-effort and local to the state path/PID namespace; it does not make multi-host or independent-state-path publishers safe.
- `/ready` validates current file-backed state load/write capability before accepting event traffic and becomes non-ready after detected state write failures. It does not prove n8n repository writes and JSON checkpoints can commit atomically.
- Recovery from `409 SYNC_REVISION_CONFLICT`, stale publisher state restore, lost queue events, or deleted/corrupt state requires stopping duplicate publishers, restoring the matching state files when available, comparing source/target state, and manually repairing or running a full source resync. Do not delete tombstone state unless you accept that stale source events can be applied again.

### Publisher invalid-state recovery

When the parsed `SYNC_PUBLISHER_STATE_PATH` file matches no known publisher state shape (supported versions `1`, `2`, `3`), the publisher quarantines it via atomic rename to `<statePath>.corrupt.<UTC-timestamp>.bak` (the original path is renamed, never overwritten or deleted in place; if quarantine itself fails the original is left in place and the error says so), reports degraded `invalid_state` status, and never throws to n8n. The error names the parsed `version` (or its JSON type when absent), a stored `sourceId` preview, the entity-key count, the state path, the supported versions, and recovery steps.

1. **Back up first.** Copy the live state file and any `.corrupt.*.bak` backup aside before any rollout or surgery.
2. **Inspect the parsed version fields.** A stored version outside `1, 2, 3` against an older bundle usually means bundle skew (the image predates the on-disk format), not corruption.
3. **On skew, rebuild/redeploy.** Build current bundles, bake both into the image, and roll the publisher; a valid v3 file loads untouched (v1/v2 migrate to v3 using the configured `SYNC_SOURCE_ID`).
4. **On genuine corruption, restore or resync.** Restore the quarantined backup after upgrading to a bundle that supports the stored version, or start a new epoch (below) and run a full subscriber resync.

Epoch rotation (`SYNC_PUBLISHER_INVALID_STATE=quarantine-reset`): counters reinit from zero only when the configured `SYNC_SOURCE_ID` differs from the quarantined file's stored `sourceId`. The reset logs a warn with `previousSourceId`, `newSourceId`, `quarantinedBackupPath`, and `invalidStateMode`; a full subscriber resync is mandatory before trusting convergence. A same-identity reset is refused at startup, as is a reset when the quarantined file carries no usable stored identity — reused `eventId`/`entityRevision` values under one source identity are rejected by the subscriber as stale/conflict (`409 SYNC_REVISION_CONFLICT`), causing silent divergence. Successful boot logs `publisherStateVersion`, `publisherStateSourceId`, `publisherNextEventSequence`, `publisherEntityKeyCount`, and `invalidStateMode` at info; the degraded-state warn keeps its structure and adds `invalidStateMode` plus `quarantinedBackupPath` when a reset was reported.

## Limitations

- **Deactivation does not sync.** n8n fires no external hook on workflow deactivation; the target corrects state on the next update/activate event (or stays active until then).
- **`workflow.activate` fires pre-commit.** If a later hook rejects the activation, the subscriber may briefly hold an uncommitted state; the next event converges it.
- **Active state is DB-only.** With `SYNC_APPLY_ACTIVE_STATE=true`, the target's `active` flag is written to the database, but triggers/webhooks are not registered with the target's active workflow manager until restart or manual toggle. Keep it `false` for passive-standby targets.
- **Execution sync requires workflow sync.** `SYNC_ENTITIES` cannot enable `executions` without also enabling `workflows`; startup fails fast on that invalid configuration.
- **Disabled subscriber entities reject valid events.** A subscriber configured without an entity family returns `422 SYNC_ENTITY_DISABLED` for that family after auth and wire validation, without touching repositories, execution identity state, or durable ordering state.
- **Execution sync is summary-only.** `SYNC_ENTITIES=…,executions` upserts a row in the target's `execution_entity` table using a target-generated id recorded in the file-backed source-execution mapping, plus the scalar lifecycle columns. The `execution_data` blob (per-step run data and the workflow snapshot at run time) is **not** written; target-side reads via the Public API will see the execution summary but not its run detail.
- **Malformed execution summaries are rejected.** The subscriber rejects execution events that omit `workflowId`, carry no lifecycle timestamps, or refer to a target workflow that does not exist yet. The request is not acknowledged as success, so the publisher keeps retrying instead of silently dropping the configured event.
- **Terminal execution rows do not regress.** Once the target holds a terminal execution (`success`, `error`, `crashed`, `canceled`) with a terminal timestamp, a later non-terminal or timestamp-less event is ignored even if its `entityRevision` is newer.
- **Workflow deletion removes synced executions first.** Before applying `workflow.delete`, the subscriber deletes mapped synced execution rows for that source/workflow so the target workflow delete does not fail on dependent execution rows.
- **Execution staleness still uses `stoppedAt` for terminal-to-terminal updates.** When both the stored row and incoming event are terminal, the row-level timestamp guard still treats `stoppedAt` as the last-write-wins field. If revision ordering already accepted the incoming event as newer, equal `stoppedAt` values are allowed and older `stoppedAt` values are rejected without advancing the subscriber checkpoint.
- **Workflow and credential ownership is best effort.** Upserts attempt to create or move the `*:owner` relation to `SYNC_TARGET_PROJECT_ID`, or to the lazily resolved owner personal project when no target project is configured. Owner lookup misses are cached for the process lifetime, owner-link failures are logged, and the event can still be checkpointed, so redelivery may not repair orphaned rows until later persistence work makes owner linkage retryable and transactional.
- **Source ownership policy is provisional in production.** The accepted policy is multi-source aggregation with source-bound credentials, target-generated workflow/credential IDs, and durable ownership mappings, but production code has not implemented `IDENTITY-02` yet. Today workflow and credential upserts, archives, and deletes still operate on source-provided target IDs after authentication and ordering checks, so native-row and cross-source collision risks remain residual blockers.
- **Wire compatibility changed.** Publisher and subscriber upgrades must roll out together. The subscriber now requires `eventId` and `entityRevision` on every event; an older publisher will be rejected as an invalid payload.
- **Revision conflicts require operator recovery.** `409 SYNC_REVISION_CONFLICT` means the target already committed that source/entity revision under a different `eventId`, usually because multiple publisher processes allocated revisions for the same `SYNC_SOURCE_ID` or a publisher was restored with stale state. Stop the extra publisher or restore the correct `SYNC_PUBLISHER_STATE_PATH`, compare source and target state, repair or resync the affected entity manually, then let the next publisher mutation emit a higher revision. Running multiple publishers for the same source identity without a shared atomic allocator is not supported.
- **Source rotation is explicit.** To intentionally change `SYNC_SOURCE_ID`, stop the publisher, back up and move aside the old `SYNC_PUBLISHER_STATE_PATH`, configure the new source ID, and run a full subscriber resync or source-retirement procedure so delayed events from the old source epoch cannot override current state. Reusing the old state file with a different source ID fails startup with migration guidance.
- **Publisher multi-process allocation is not supported.** The file-backed publisher allocator creates a best-effort lock next to `SYNC_PUBLISHER_STATE_PATH` and rejects another live process sharing that state path. If startup fails on a verified stale lock after a crash, stop duplicate publishers first, then remove only the `.lock` file and restart. This lock is not a substitute for an atomic transactional outbox or shared revision allocator.
- **Subscriber ordering format-1 state blocks startup/event handling.** Back up the old file, then either restore an operator-maintained unambiguous metadata backup or reset the subscriber state file and perform a full source resync. Automatic migration is intentionally not attempted because version-1 tombstone keys can alias when source IDs or entity IDs contain colons.
- **Replay rejection is HMAC-only and process-local.** Exact signed replays are rejected only in `hmac` mode and only while this process's replay cache still remembers that signature. `SYNC_REPLAY_CACHE_SIZE` bounds completed successful entries; in-flight entries are transient and are not evicted before completion/release, so an identical concurrent request in the same process cannot also mutate state. A successful request stays remembered until `SYNC_SIGNATURE_TOLERANCE_MS` expires or `SYNC_REPLAY_CACHE_SIZE` evicts it. If parsing, validation, or application fails, the reservation is released and the exact request may be retried. The replay cache is not shared across OS processes or after restart, so run one subscriber process per route unless a future shared durable replay store is added. Durable ordering still makes stale re-delivery a no-op after cache expiry or restart.
- **Ordering state must be on persistent storage.** If `SYNC_PUBLISHER_STATE_PATH` or `SYNC_SUBSCRIBER_STATE_PATH` points at ephemeral storage, restarts can forget counters, source identity, or tombstones and weaken stale-event protection until newer revisions arrive.
- **Credential sync requires a shared `N8N_ENCRYPTION_KEY`** on all instances.
- **Credential create publication requires a stable source id.** On the pinned n8n `2.31.2` hook contract, this means the payload must include `credential.id` directly or expose it soon after commit through `dbCollections.Credentials.findOne({ where: { id } })`. Payloads without `id` are logged and dropped to avoid publishing another credential's data.
- **The delivery queue is in-memory and bounded.** Events queued but not yet delivered when the source instance restarts are lost. If `SYNC_MAX_QUEUE_SIZE` is exceeded, the oldest queued event for that target is dropped and logged before enqueueing the new one. Later upserts may still converge state, but dropped deletes, archives, or other mixed operations are not reconstructed automatically.
- **Tag filtering is source-side only.** `SYNC_FILTER_BY_TAG` rewrites the publisher's DTOs and may turn an upsert into a delete; the subscriber never sees or honors tag fields. Tagging a workflow on the source does not propagate the tag itself to the target.

## Development

```bash
pnpm build       # bundle dist/publisher.cjs + dist/subscriber.cjs (single-file CJS)
pnpm test        # unit tests
npx tsc --noEmit -p tsconfig.json         # typecheck src
npx tsc --noEmit -p tsconfig.tests.json   # typecheck src + tests
pnpm test:integration # repo root: runs the supported pinned n8n version matrix
```

Release packaging uses the checked-in `release:materialize` step to copy the repo `VERSION`, license, author, and package directory repository metadata into this package manifest before packing. `pnpm pack:verify` materializes that metadata, builds through `npm pack`, inspects the exact generated tarball contents, installs that tarball into a temporary CommonJS consumer that requires both subpath exports, and verifies the packed publish metadata locally.
